## Requirement understanding

One line: Add a `exo_add_tenant_block_list_entry` tool to the Exchange Online MCP connector so the platform can add a sender (or URL/file hash) to the tenant-wide Tenant Allow/Block List — the second step of the "remove malicious email and block sender" offboarding-style workflow that today has no corresponding tool.

Source: item 55 of `mspbots-gap-register.xlsx` (Rewst → MSPbots migration gap list), Rewst account "EMD Networking Services". The gap is classified `tool` — the connector (Exchange Online) already exists, only this one tool is missing. The reporter's worked example is the Rewst flow `[ROC] M365: Remove Malicious Emails and Block Sender` (EMD Networking Services, ~365 executions/year, evidence grade A), which calls the Rewst action `microsoft_exo.exo_invoke_command` with cmdlet `New-TenantAllowBlockListItems`, parameters `{"Block": true, "Entries": ["{{ CTX.sender }}"], "ListType": "Sender", "NoExpiration": true}`. The reporter also names `Url`/`FileHash` as acceptable alternative `ListType` values, `ExpirationDate` as an alternative to `NoExpiration`, and an optional `Notes` field; and lists the fields the downstream workflow consumes from the response: the created block item's `Identity`, `Value`, `ListType`, `ExpirationDate`.

## Product design

### Goals / Non-goals

**Goals**

- `exo_add_tenant_block_list_entry(list_type, entries, no_expiration=False, expiration_date=None, notes=None)` — creates one or more tenant-wide **Block** entries in the Tenant Allow/Block List, completing the second step of the reporter's offboarding-style "remove malicious email, then block the sender" workflow.
- `list_type` restricted to the three values the ticket names: `Sender`, `Url`, `FileHash`.
- Idempotent: an entry already on the block list for the same `list_type` is reported `already_blocked`, never as an error.
- Bulk-safe: multiple `entries` in one call are evaluated independently — a duplicate or malformed entry does not fail the other entries in the same call (mirrors `exo_add_email_alias`'s per-address partial-success contract).
- `no_expiration` / `expiration_date` mutually exclusive, matching the ticket's own two parameter sets; an `expiration_date` with no timezone offset is rejected rather than guessed (same rule `exo_set_auto_reply` already enforces for its own date/time parameters).
- Response surfaces exactly the fields the reporter's workflow consumes: `identity`, `value` (the entry), `list_type`, `expiration_date`, plus `notes` when set.

**Non-goals**

- `Set-TenantAllowBlockListItems` (editing an existing entry's expiration/notes without removing it) — not requested; flagged as a follow-up ticket candidate.
- `Remove-TenantAllowBlockListItems` (un-blocking) — not requested.
- A standalone `exo_get_tenant_block_list_items` read tool — not requested as its own tool. `Get-TenantAllowBlockListItems` is still called, but only internally as a precondition check (same convention as `mailbox.py`'s internal `_read_mailbox` and `permissions.py`'s internal `Get-Recipient` delegate check — neither of those is a public tool either).
- `ListType=IP` — the cmdlet supports it, the ticket does not ask for it. Open Question below.
- `ListSubType=AdvancedDelivery` (phishing-simulation allow-listing) — only applies to `Allow`, and this tool is Block-only.
- The `Allow` direction — the tool name and every worked example in the ticket are block-only. `Block` is fixed `true`, not a caller-settable parameter (same "fixed right, not caller-settable" shape `exo_add_mailbox_permission` already uses for `AccessRights=["FullAccess"]`).

### Acceptance criteria AC1..AC13

- **AC1**: Given `list_type="Sender"`, `entries=["attacker@contoso.com"]`, `no_expiration=true`, and no existing block entry for that sender, When `exo_add_tenant_block_list_entry` is called, Then the response reports that entry with `result="added"`, and includes its `identity`, `value`, `list_type="Sender"`, `expiration_date=null`.
- **AC2**: Given a sender already on the tenant block list, When `exo_add_tenant_block_list_entry` is called again for the same `list_type` and value, Then the response reports `result="already_blocked"` for that entry and no new `New-TenantAllowBlockListItems` call is issued for it.
- **AC3**: Given two entries in one call, one new and one already blocked, When the tool is called, Then both are reported independently (`added` / `already_blocked`) in the same response — the duplicate does not prevent the new one from being written.
- **AC4**: Given `entries=[]`, When the tool is called, Then the response is `error.code="invalid_argument"` before any upstream call is made.
- **AC5**: Given `list_type` outside `{Sender, Url, FileHash}` (e.g. `"IP"` or a typo), When the tool is called, Then the response is `error.code="invalid_argument"` naming the three supported values.
- **AC6**: Given both `no_expiration=true` and a non-null `expiration_date`, When the tool is called, Then the response is `error.code="invalid_argument"` stating the two are mutually exclusive — no upstream call is made.
- **AC7**: Given `expiration_date` without a timezone offset (e.g. `"2026-12-01T00:00:00"`), When the tool is called, Then the response is `error.code="invalid_argument"` — the value is rejected, never silently assumed to be UTC or local time.
- **AC8**: Given neither `no_expiration` nor `expiration_date` is supplied, When the tool is called, Then neither parameter is sent upstream, and the response surfaces whatever `ExpirationDate` Exchange itself assigns (Microsoft's documented default is a 30-day expiry for Block entries) — the tool does not invent or hard-code a default.
- **AC9**: Given no Exchange Online credentials on the request, When the tool is called, Then the response is `error.code="not_configured"` (same `NO_CREDENTIALS` envelope every other tool in this connector returns).
- **AC10**: Given the app-only credential has Exchange Administrator but **not** Security Administrator / Organization Management, When the tool is called, Then the response is `error.code="unauthorized"` whose message explicitly names the Security Administrator (or Organization Management) role requirement — a generic "unauthorized" would mislead an operator who already granted this connector's documented default role.
- **AC11**: Given `notes="requested by SOC"`, When a new entry is added, Then the submitted notes are forwarded to Exchange and echoed back in the response for that entry when Exchange returns them.
- **AC12**: The new tool has exactly one row in `README.md`'s Tools table and exactly one row in `docs/gdap-role-map.yaml`, both stating GDAP role **Security Administrator** — distinct from the other 18 tools' **Exchange Administrator** — and the connector's own three-way consistency test (`tests/test_gdap_role_map.py`) passes with this mixed-role reality, not by weakening the test to stop checking roles.
- **AC13**: Given one entry in a multi-entry call is rejected by Exchange with a per-entry error (e.g. a malformed value) while the rest succeed, When the tool is called, Then the rejected entry is reported `result="invalid"` with Exchange's message, and the other entries in the same call still succeed — one bad entry does not fail the whole call.

### Open questions

- **[non-blocking]** `ListType=IP` is not requested by the ticket and is left out of this design's scope, consistent with the explicit three values (`Sender`, `Url`, `FileHash`) named in the ticket's own `ListType*` field description. If a future ticket wants IP blocking, it is an additive, backward-compatible enum extension to this same tool.
- **[non-blocking]** Whether `Get-TenantAllowBlockListItems` needs an explicit `Action=Block` filter to avoid matching an `Allow` entry with the same value, or whether `ListType` alone is a sufficient precondition-read filter, is not confirmed against a live tenant (none reachable from the design flow). The dev leg verifies this empirically against the mocked-upstream test harness and, if the cmdlet returns both Allow and Block entries for a `ListType` query, filters client-side on the record's `Action` field before treating a hit as "already blocked" — the existing `project()` field-whitelist mechanism already supports this without new infrastructure.
- **[non-blocking]** The precise GDAP/Entra role string (`Security Administrator` vs. `Organization Management` vs. both) could not be checked against this org's live GDAP role catalog from the design flow. This design documents `Security Administrator` as the primary role (Microsoft's own configuration guide lists it first and most consistently across the three permission surfaces — Exchange role groups, Entra roles, and Defender XDR Unified RBAC) with `Organization Management` as an accepted alternative, matching the existing `gdap-role-map.yaml` schema's `roles: [...]` list shape (see `exo_list_gdap_roles`'s `roles: null` for the precedent that this field already varies per tool).

## Tech design

### Conclusion

Add one new tool, `exo_add_tenant_block_list_entry`, in a new module `src/exo_mcp/tools/tenant_allow_block_list.py`, following this connector's established precondition-read-then-write idempotent-add pattern (`groups.py`, `mailbox.py`). No new HTTP client, base URL, or auth mechanism is needed — the cmdlet runs through the same `ExoClient.invoke()` every other tool already uses. The one real complication is that this tool needs a **different GDAP role** than all 18 existing tools, which breaks a hard-coded "all tools need Exchange Administrator" assumption baked into this connector's own test suite and README prose — both must be generalized, not just extended, or the connector's own correctness check (AC12 / `test_gdap_role_map.py`) would either fail outright or (worse) be "fixed" by silently forcing the wrong role onto the new tool to make the old assertion keep passing.

- Tools: `src/exo_mcp/tools/{mailbox,groups,devices,permissions,gdap_roles}.py`
- Registration: `src/exo_mcp/server.py:148-152`
- HTTP/cmdlet client: `src/exo_mcp/api_client.py` (`ExoClient.invoke`, `src/exo_mcp/api_client.py:198-224`)
- Shared helpers: `src/exo_mcp/tools/_common.py` (`project`, `contains_case_insensitive`, `NO_CREDENTIALS`)

### Option analysis

**Precondition check before write — Option A (chosen): read via `Get-TenantAllowBlockListItems`, write only the unseen entries in one bulk `New-TenantAllowBlockListItems` call.**

All `entries` in a single tool call share the same `no_expiration` / `expiration_date` / `notes` options, so one write call can cover every new entry (the cmdlet's own `-Entries` parameter is already an array) — no need to call `New-TenantAllowBlockListItems` once per entry. This keeps the call count fixed at 2 (one read, one write) regardless of how many entries are passed, matching this connector's existing cost profile for its other write tools.

- **Option B (rejected): skip the precondition read; call `New-TenantAllowBlockListItems` directly and parse Exchange's own "already exists" error text per entry.** Rejected because, unlike the TOCTOU-fallback role text-matching plays elsewhere in this connector (`groups.py`'s `_DUPLICATE_MEMBER_MARKERS`, explicitly documented there as "no confirmed upstream wording exists... not the primary idempotency mechanism"), there is **no confirmed duplicate-entry error text for this cmdlet at all**, and Microsoft's own documentation suggests a duplicate add may not uniformly error (some automation scripts in the wild `Remove-`-then-`New-` instead of relying on an error). Making the precondition read optional/fallback here would be assigning confidence this cmdlet's behavior doesn't support.
- **Option C (rejected): expose `Get-`/`Set-`/`Remove-TenantAllowBlockListItems` as additional public tools in this same ticket.** Not requested — the ticket names exactly one tool. `Get-` is still called, but only as internal plumbing (same convention as `mailbox.py`'s `_read_mailbox`, `permissions.py`'s internal `Get-Recipient` check), not a new public surface. Listed as a follow-up candidate, not built here (YAGNI).

### Data & API contract

**Tool signature**

```python
async def exo_add_tenant_block_list_entry(
    list_type: Literal["Sender", "Url", "FileHash"],
    entries: list[str],
    no_expiration: bool = False,
    expiration_date: str | None = None,   # ISO-8601 with a timezone offset, e.g. "2026-12-01T00:00:00+00:00"
    notes: str | None = None,
) -> str
```

**Upstream calls**

1. Precondition read: `Get-TenantAllowBlockListItems` with `{"ListType": list_type}` (plus, per Open Question 2, a client-side filter on the record's `Action` field to `Block` if the cmdlet does not filter server-side). Result projected through `project()` onto `{Identity, Value, ExpirationDate, Notes, Action}`; entries whose `Value` matches (case-insensitively, via `contains_case_insensitive`) a requested entry are excluded from the write set and reported `already_blocked`.
2. Write (only if at least one entry is new): `New-TenantAllowBlockListItems` with
   ```json
   {"ListType": "<list_type>", "Entries": ["<new entries only>"], "Block": true,
    "NoExpiration": true | null, "ExpirationDate": "<UTC ISO-8601>" | null, "Notes": "<notes>" | null}
   ```
   `Block` is always sent `true` — fixed, not caller-settable (same convention as `exo_add_mailbox_permission`'s fixed `AccessRights`). `NoExpiration` / `ExpirationDate` / `Notes` are omitted (not sent as explicit `null`) when not supplied — `invoke()` already drops `None` parameters (`api_client.py` behavior reused unchanged), which is exactly AC8's "don't invent a default" requirement.

**Response envelope** (mirrors `exo_add_email_alias`'s `{identity, results[], accepted}` shape, substituting the mailbox-scoped `identity` key for the tenant-scoped `list_type`):

```json
{
  "list_type": "Sender",
  "results": [
    {"entry": "attacker@contoso.com", "result": "added", "identity": "...", "value": "attacker@contoso.com", "expiration_date": null, "notes": null},
    {"entry": "spam@evil.example", "result": "already_blocked", "identity": "...", "expiration_date": "2026-11-15T00:00:00Z"},
    {"entry": "", "result": "invalid", "message": "<Exchange's per-entry error text>"}
  ],
  "accepted": true
}
```

`accepted` is `true` if at least one entry was newly written or already compliant (`added`/`already_blocked`); `false` only if every entry in the call was `invalid` and nothing was written — mirrors `exo_add_email_alias`'s `accepted` semantics exactly.

**Error codes**: reuses `invalid_argument` (AC4–AC7), `unauthorized` (AC10, message customized to name Security Administrator — reusing `groups.py`'s `_membership_error`-style 403-remapping pattern, since the generic message would wrongly suggest Exchange Administrator is sufficient here), `not_configured` (AC9), `rate_limited`, `upstream_error`. No new error codes are introduced.

**Backward compatibility**: purely additive at the API level — new tool, new yaml row, new README row, no existing tool's contract changes. The one test-level change with no runtime-behavior impact is generalizing `test_all_18_real_tools_map_to_exchange_administrator` (Change list item 5).

**No DB/schema changes** — this connector is stateless; the Tenant Allow/Block List itself lives entirely in Exchange Online.

### Key flow / sequence

```
caller -> exo_add_tenant_block_list_entry(list_type, entries, ...)
  1. validate: entries non-empty, list_type in {Sender,Url,FileHash},
     no_expiration/expiration_date mutually exclusive, expiration_date has a tz offset
     -> invalid_argument, no upstream call, on any failure (AC4-AC7)
  2. client = client_factory(); None -> NO_CREDENTIALS (AC9)
  3. Get-TenantAllowBlockListItems(ListType=list_type)
     -> partition entries into already_blocked (case-insensitive match) vs new
  4. if new is non-empty:
       New-TenantAllowBlockListItems(ListType, Entries=new, Block=true,
                                      NoExpiration|ExpirationDate, Notes)
       -> per-entry result: added | invalid (AC1, AC3, AC13)
       -> ExoError(403) remapped to a Security-Administrator-naming message (AC10)
  5. merge already_blocked + new-write results -> single results[] response (AC2, AC3)
```

### Non-functional

- **Multi-tenant isolation**: unaffected. Credentials still flow exclusively through `server.py`'s per-request contextvar (`_credentials_var`); this tool takes no shortcut around it and introduces no module-level state.
- **Idempotency/concurrency**: the precondition-then-write sequence has the same TOCTOU window this connector already accepts for `groups.py` and `mailbox.py`'s add tools (two concurrent calls could both read "not present" and both write) — an accepted, non-blocking, inherited risk, not introduced by this design.
- **Performance**: 2 upstream calls per tool invocation regardless of how many entries are passed (bulk `Entries` array) — same complexity class as every other write tool here, no N+1 pattern.
- **Security**: `entries` values (sender addresses, URLs, file hashes) are operator-supplied threat-intel data, not secrets. No special handling beyond this connector's existing "credentials only from headers, never logged" rule, which this tool does not touch.
- **Observability**: none added beyond the existing structured error envelope — matches this repo's documented baseline ("no logging framework exists in this repo today", PRD-20394 Tech design), not a regression introduced here.
